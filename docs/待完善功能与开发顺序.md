## 架构整理规划

当前 `src/features/{auth,projects,tasks}/api/` 已按业务功能拆分，负责在浏览器里调用 Supabase；它们不是服务端 API。Supabase 已提供 HTTP 数据接口、认证和 PostgreSQL，因此不额外引入 Axios、Express、Prisma 或空置的 Repository/Service 层。

后续按实际复杂度做小步整理：

1. **先按页面拆分 `App.tsx`**：路由保留在 `src/app/`，项目页、看板页、设置页分别放回对应 feature 的 `pages/`。页面负责组合页面组件和 hooks，不集中承载所有 JSX。
2. **抽取 TanStack Query hooks 和 query keys**：项目查询/变更放入项目 feature；任务/评论查询/变更放入任务 feature。统一缓存键和失效时机，API 模块继续只负责 Supabase 数据请求与结果映射。
3. **实现权限时再集中界面判断**：项目/任务 UI 根据已加载的角色决定是否显示操作；真正的授权仍由数据库 migration 中的 RLS 和 GRANT 执行。不能用前端 `permission.ts` 代替数据库安全规则。
4. **只在出现复用或复杂编排时加 service**：例如一个业务操作需要多次读写、事务或复用规则时，再添加对应领域的 service/RPC；简单 CRUD 不套 Repository Pattern。
5. 每一步单独检查 diff 和页面行为，相关功能完成后再运行匹配的 lint/build/test；保持可以逐步 review 和提交。

建议的轻量目标结构（`src/api/index.ts` 是长期候选，确定 feature 的公开导出边界后再引入）：

```text
src/
  app/                         # 路由与全局 Provider
  api/index.ts                 # 可选的应用级公开 API 出口，便于发现与稳定导入
  lib/supabase.ts              # Supabase 客户端
  features/
    auth/{api,hooks,pages}/
    projects/{api,hooks,pages,components}/
    tasks/{api,hooks,pages,components,store}/
supabase/migrations/           # 表、函数、GRANT、RLS 的版本化 SQL
```

统一转出口的长远价值是形成稳定导入边界和可供 review 的能力目录：调用方可以从 `src/api/index.ts` 或 feature 的公开 `index.ts` 看见项目对外提供哪些数据操作，内部文件以后拆分时调用方不必跟着改路径。它本身不执行请求、不增加安全性；导出边界尚未稳定前先画清职责，避免只多一个转发文件。

优先级上，先完成邀请加入和关闭公开加入，再增加需要的前端角色入口；页面/Query 分拆和统一导出口排在权限任务之后。暂不增加通用 HTTP 拦截器、Prisma、领域实体或多层仓储抽象；出现对应的业务需求后再评估。
