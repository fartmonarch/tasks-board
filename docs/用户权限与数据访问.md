# 用户权限与数据访问

> 核对日期：2026-09-30。本文描述当前 Supabase 数据库与前端的实际权限边界。新增或修改权限时，同时更新迁移和本文。

## 1. 先区分登录与数据权限

Supabase Auth 负责注册、登录和签发用户 JWT。JWT 让数据库识别 `auth.uid()`；它不会自动决定用户能读写哪些业务数据。业务访问由 PostgreSQL 表授权（`GRANT`）和 RLS 策略共同决定：两层都允许，请求才会成功。

- `anon`：未登录访问者。业务表不授予其访问权限。
- `authenticated`：已登录账号。仅获得应用需要的表/列权限，并继续受 RLS 行策略限制。
- `service_role`：受信任服务端使用的管理角色。不得放入浏览器、`VITE_*` 环境变量或前端代码。
- 团队角色：`team_members.role` 当前只有 `admin` 和 `member`。
- 项目成员：`project_members` 代表项目访问关系；当前没有独立的项目管理员角色，团队管理员可以管理团队内项目和项目成员。

## 2. 主要关系与显示名称

| 表 | 用途与关键关系 |
| --- | --- |
| `profiles` | 用户资料。`id` 对应 `auth.users.id`；`display_name` 是用户显示名称。 |
| `teams` | 团队；`created_by` 是创建者。 |
| `team_members` | 团队与用户关系，含 `admin` / `member` 角色。 |
| `projects` | 项目属于一个团队；同一团队的项目名不区分大小写且忽略首尾空格后必须唯一。 |
| `project_members` | 项目授权成员；只能加入该团队的成员。 |
| `tasks` | 项目任务；负责人字段是 `assignee_user_id`，通过复合外键关联该项目的 `project_members`。 |
| `comments` | 任务评论；`author_id` 关联 Auth 用户，访问范围继承任务所属项目。 |

负责人姓名不重复存进 `tasks`。任务保留稳定的用户 ID，界面通过 `profiles.display_name` 显示姓名。这样改名后历史任务也会显示新名字，且不能把项目外的任意账号指派进来。新用户登录后会补齐自己的资料；本人可在“设置我的显示名称”中修改。

## 3. 当前授权矩阵

| 数据 | 未登录 / `anon` | 已登录但无关联 | 团队成员 | 项目成员 | 团队管理员 |
| --- | --- | --- | --- | --- | --- |
| `profiles` | 无权访问 | 只能访问本人资料 | 可读取共同团队用户资料 | 可读取符合共同团队策略的资料 | 同团队读取范围；本人可修改本人 `display_name` |
| `teams` | 无权访问 | 只能创建由自己作为 `created_by` 的团队，不能读取别人的团队 | 可读所在团队 | 可读其所属团队 | 可读、改名、删除其管理的团队 |
| `team_members` | 无权访问 | 无权访问 | 可读取团队成员 | 同团队规则 | 可新增、调整、移除团队成员 |
| `projects` | 无权访问 | 无权访问 | 没有项目成员关系时不可读项目 | 可读取授权项目 | 可读取、创建、改名、删除团队内项目 |
| `project_members` | 无权访问 | 无权访问 | 无项目权限时不可读写 | 可读取授权项目成员 | 可添加、移除项目成员 |
| `tasks` | 无权访问 | 无权访问 | 只有管理员按团队项目策略可访问 | 可读取、创建、修改、删除授权项目任务 | 可访问团队项目任务 |
| `comments` | 无权访问 | 无权访问 | 只有具备对应项目访问权才可访问 | 可读取并以本人身份新增评论 | 可访问团队项目评论 |

补充限制：

- 新建团队时，创建者被记录为团队管理员；新建项目时，创建者加入该项目。
- 创建、修改任务受项目访问策略约束；创建任务时 `created_by` 必须是当前登录用户。
- 负责人可以为空；非空时必须是项目成员。移除负责人后任务保留，负责人变为未分配。
- 评论只开放读取和新增；当前没有评论编辑、删除接口。
- 团队或项目删除会通过外键级联删除下游成员/任务/评论数据；界面删除流程尚未实现，未来增加前必须提供明确确认。

## 4. 表/列授权与 RLS

业务表先撤销 `anon`、`authenticated` 和 PostgreSQL `PUBLIC` 的默认权限，再向 `authenticated` 授予最小权限；所有业务表启用 RLS。列级权限是有意的，例如 `profiles`：

- `SELECT`：读取操作由 `profiles_select_shared_team` 控制。
- `INSERT(id, display_name)`：`profiles_insert_self` 只允许 `id = auth.uid()`。
- `UPDATE(display_name)`：`profiles_update_self` 只允许修改本人的资料；不授予修改 `id` 的权限。

“permission denied for table profiles” 的已定位原因：前端曾用 `upsert(..., onConflict: "id")`。冲突合并会要求更新冲突列 `id`，但设计上只允许更新 `display_name`。当前实现改为缺少资料时 `INSERT`、资料为空时只 `UPDATE(display_name)`，不扩大用户 ID 的更新权限。

`create_team` 与 `create_project` 是 `SECURITY INVOKER` RPC：以调用者权限运行，底层插入仍必须通过 RLS。`private` schema 内固定用途的 `SECURITY DEFINER` 辅助函数只返回权限判断结果，不在公开 Data API schema 中提供业务 RPC。

## 5. 当前尚未覆盖的权限场景

- 目前没有团队邀请、加入申请或项目成员管理 UI；创建者以外的用户尚无完整加入流程，因此也无法被指派为负责人。
- 没有完整的多账号自动化验证；“用户 A、用户 B、非成员”读写边界还需单独验收。
- 团队所有权转移、管理员离开/删除、最后管理员保护、删除账号后的数据归属尚未设计。
- SMTP 暂缓；真实邀请邮件需要受信任服务端（如 Edge Function）和邮件服务。管理密钥不得放进前端。
- Auth 的泄露密码保护当前未启用；这是独立的 Auth 加固项，不影响上述业务表 RLS。

## 6. 改权限时的规则

1. 在 `supabase/migrations/` 新建迁移，不只在 Dashboard 手工改线上表。
2. 每项变更同时检查表/列 `GRANT`、RLS 的 `USING` / `WITH CHECK`、外键和级联行为。
3. 不用 service role 绕过前端权限；不为了消除 RLS 错误而无条件授予 `anon` 或所有已登录用户。
4. 变更身份、成员或删除权限时，覆盖创建者、管理员、普通成员、项目成员、无关账号五类场景。
5. 报错时同时区分 SQL 权限不足、RLS 拒绝、外键/唯一约束失败，不能把它们统称为“登录问题”。
