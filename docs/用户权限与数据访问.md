# 用户权限与数据访问

> 核对日期：2026-09-30。当前权限模型只围绕项目成员；团队和团队成员表已从远程数据库删除。

## 身份与数据模型

Supabase Auth 负责登录并提供 `auth.uid()`。表授权（`GRANT`）和 RLS 一起决定数据访问。

| 表 | 用途 |
| --- | --- |
| `profiles` | 用户显示名称，用户本人可修改。 |
| `projects` | 项目名称与创建者。所有登录用户可浏览项目 ID 和名称；创建者可改名、删除。 |
| `project_members` | 项目与用户的访问关系；成员只能为本人加入，不能替别人加入或移除成员。 |
| `tasks` | 项目任务；非空负责人必须是该项目成员。 |
| `comments` | 任务评论；访问范围继承任务所属项目。 |

团队模式迁移将原项目创建者、原团队管理员补为对应项目成员，保留项目权限；原项目成员、项目、任务和评论均保留。团队名称及仅有团队级别的成员记录已删除。

## 授权规则

| 数据 | 未登录 | 登录但未加入项目 | 项目成员 | 项目创建者 |
| --- | --- | --- | --- | --- |
| 项目列表 | 无权访问 | 可读项目 ID 和名称 | 可读 | 可读、创建、改名、删除 |
| 项目成员 | 无权访问 | 只能读自己的成员关系，可为自己加入 | 可读取项目成员 | 同项目成员规则 |
| 任务与评论 | 无权访问 | 无权访问 | 可读写项目任务；评论可读和新增 | 同项目成员规则 |
| 用户资料 | 无权访问 | 只能读本人 | 可读同项目用户 | 同项目成员规则 |

所有登录用户可浏览项目名称并自行加入。项目加入在 `project_members` 上直接插入当前用户 ID，数据库 RLS 强制 `user_id = auth.uid()`；重复加入由主键冲突处理为幂等成功。加入后该用户才能读取项目任务、评论和同项目成员资料。

如果 Auth 保持开放注册，任何新注册账号都可以看到项目名称并加入项目。项目数据仍受 RLS 保护，但这是开放加入模式的产品边界。

## 表授权和 RLS

- 未登录角色不获授业务表访问权限；`service_role` 不进入浏览器或 `VITE_*` 环境变量。
- `projects` 仅向 `authenticated` 授予读取 `id`/`name`，以及创建项目、修改/删除本人创建项目所需列权限。
- `project_members` 仅允许读取自身成员关系或已加入项目的成员关系；插入时必须是本人 ID，没有客户端删除权限。
- `tasks`、`comments` 的 RLS 通过 `private.can_access_project` 和 `private.can_access_task` 确认项目成员身份。
- `profiles` 只允许本人插入和更新；资料读取仅限本人和共同项目成员。
- `create_project(text)` 是 `SECURITY INVOKER` RPC：插入项目并在同一事务中加入创建者，项目插入和成员插入都继续受 RLS 约束。

## 权限变更约定

1. 在 `supabase/migrations/` 创建迁移，并确认远程项目和本地迁移版本一致。
2. 检查列级 `GRANT`、RLS 的 `USING`/`WITH CHECK`、外键和删除级联。
3. 不把管理密钥放入浏览器；不以扩大到 `anon` 权限来修复访问错误。
4. 至少复核项目创建者、已加入成员、未加入用户和未登录用户的访问范围。
