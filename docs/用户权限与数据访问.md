## 身份与数据模型

Supabase Auth 负责登录并提供 `auth.uid()`。表授权（`GRANT`）和 RLS 一起决定数据访问。

| 表 | 用途 |
| --- | --- |
| `profiles` | 用户显示名称，用户本人可修改。 |
| `projects` | 项目名称与创建者。登录用户仍可浏览项目 ID 和名称；owner 可改名，系统管理员可管理并删除所有项目。 |
| `project_members` | 项目与用户的访问关系及项目内角色 `owner/member`；用户仍可自行加入为 member。 |
| `tasks` | 项目任务；项目成员和系统管理员可访问，非空负责人必须是该项目成员。 |
| `comments` | 任务评论；访问范围继承任务所属项目。 |

团队模式迁移将原项目创建者、原团队管理员补为对应项目成员，保留项目权限；原项目成员、项目、任务和评论均保留。团队名称及仅有团队级别的成员记录已删除。

5. **SQL Editor**：可以运行下面的只读查询复核策略和权限。

### SQL Editor 中的只读检查

查看当前 `public` 表的行级策略：

```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname = 'public'
order by tablename, policyname;
```

查看表级授权：

```sql
select grantee, table_name, privilege_type
from information_schema.role_table_grants
where table_schema = 'public'
  and grantee in ('anon', 'authenticated', 'service_role')
order by table_name, grantee, privilege_type;
```

有些授权只给特定列，因此还要单独查看列级授权：

```sql
select grantee, table_name, column_name, privilege_type
from information_schema.column_privileges
where table_schema = 'public'
  and grantee in ('anon', 'authenticated', 'service_role')
order by table_name, grantee, column_name, privilege_type;
```

查看系统角色是否绕过 RLS：

```sql
select rolname, rolsuper, rolbypassrls
from pg_roles
where rolname in ('anon', 'authenticated', 'service_role')
order by rolname;
```

这些查询只读。不要把数据库密码或 `service_role` key 贴进聊天、前端代码或 Git。

## PostgreSQL 角色与应用业务角色不是一回事

线上数据库已核对的角色和使用方式：

| PostgreSQL 角色 | 用途 | 当前项目里的权限 |
| --- | --- | --- |
| `anon` | 没有登录会话的 Data API 请求 | 当前五张业务表没有授予它应用读写权限。 |
| `authenticated` | 带有效 Supabase Auth 用户会话的请求 | 获得必要表/列授权，再由 RLS 按项目 owner、普通成员或私有管理员记录判断行权限；该 PostgreSQL 角色本身不代表任何业务角色。 |
| `service_role` | 仅可信后端或 Supabase 内部管理操作使用 | 有广泛数据库权限并绕过 RLS；当前 Vercel 前端不使用它。绝不能把它放进 `VITE_*` 变量。 |

Supabase Dashboard 的项目拥有者/操作者也是平台管理权限，不是应用中登录的系统管理员。`service_role` 同样不是应用“系统管理员”角色，它是高权限技术密钥。

应用角色现由数据库记录：`project_members.role` 为 `owner` 或 `member`；全局管理员保存在未暴露给 Data API 的 `private.system_admins`。RLS 通过 `private.is_system_admin()`、`private.is_project_owner(uuid)` 和 `private.can_access_project(uuid)` 判断。客户端不能读写管理员记录，也不使用 `service_role`。

按远程数据库当前规则，应用权限可概括为：

| 表 | 登录且满足 RLS 的用户可以做什么 |
| --- | --- |
| `profiles` | 查看自己和共同项目成员的显示名；为自己创建资料、修改自己的显示名。 |
| `projects` | 所有登录用户仍可浏览 ID/名称并创建项目；owner 可改名；系统管理员可跨项目修改和永久删除。项目 owner 的归档、恢复和永久删除入口仍待后续任务。 |
| `project_members` | 查看自己的关系或有权访问项目的成员关系；仍可自行加入为 `member`；不能自行升为 owner，也没有客户端移除/转让角色权限。 |
| `tasks` | 项目成员可读写；系统管理员可跨项目管理；普通成员只可删除自己创建的任务，owner 可删除本项目任务。列授权仍限制可修改字段。 |
| `comments` | 项目成员可查看和新增本人评论；系统管理员通过任务所属项目的访问判断也可查看/新增；普通登录角色没有评论修改/删除授权及 RLS policy。 |

表/列授权和 RLS 是两层门：必须先有对应 SQL 权限，再通过行策略。例如未加入项目的用户不能读取该项目任务。项目发现和自行加入目前仍是过渡状态；下一个权限任务必须实现邀请加入并关闭公开发现/自行加入。

### 首次指定系统管理员（受信任 SQL Editor 一次性操作）

在 Supabase Dashboard → SQL Editor 执行。把邮箱字符串替换为已经存在且由你控制的 Auth 账号准确邮箱；脚本只查询现有 `auth.users`，不会创建账号。未查到或匹配不唯一时会报错并停止；不得填写猜测的 UUID。

```sql
do $$
declare
  target_user_id uuid;
  match_count integer;
begin
  select count(*)
  into match_count
  from auth.users
  where lower(email) = lower('替换为现有管理员账号的准确邮箱');

  if match_count <> 1 then
    raise exception 'Expected exactly one existing Auth user for the selected email; found %', match_count;
  end if;

  select id into target_user_id
  from auth.users
  where lower(email) = lower('替换为现有管理员账号的准确邮箱');

  insert into private.system_admins (user_id, granted_by)
  values (target_user_id, target_user_id)
  on conflict (user_id) do nothing;
end;
$$;
```

完成后可在受信任 SQL Editor 只读核验记录数。此表没有授予 `authenticated` 或 `service_role` 客户端读写权限，授权/撤销都由受信任 SQL 操作完成。

### 读懂本项目的 Supabase 和 migration

可以先用 MySQL 的经验来对照：Supabase 底层仍是 PostgreSQL 数据库，但还帮项目提供登录认证、API 接口和 Dashboard。当前 React 页面通过 `supabase-js` 发请求；Supabase Auth 验证登录并给请求附上用户 JWT；PostgREST 把请求变成数据库查询；PostgreSQL 再检查 SQL 授权和 RLS，最后才读写表。

```text
React 页面 -> supabase-js + 当前登录 JWT -> Supabase Data API -> GRANT/列权限 -> RLS -> PostgreSQL 表
```

`supabase/migrations/` 下的 SQL 文件就是有版本号的数据库变更记录，类似“可追踪、可按顺序执行的数据库升级脚本”，不是第二个数据库，也不是 React 代码。Supabase CLI 按文件名前面的时间顺序把它们应用到远程数据库，并记录已执行版本。已经应用的迁移不要回头改；后续调整另建迁移，让本地文件和线上变更历史保持一致。数据库注释迁移只补充 Dashboard 里的说明文字，不改表数据和访问规则。

看迁移时建议按这个顺序读：

1. `create table` / `alter table`：创建表或改列、约束、外键。
2. `grant` / `revoke`：规定角色是否有资格对表/列发出查询或写入操作。
3. `alter table ... enable row level security`：启用逐行访问控制。
4. `create policy`：决定哪些行可读/写。`USING` 检查现有行；`WITH CHECK` 检查写入后行是否符合规则。
5. `create function`：把重复 SQL 封装为数据库函数；本项目的 `create_project(text)` 将建项目和添加创建者成员放进一次数据库调用中。

比如，仅允许用户读取自己的资料时，策略里的 `auth.uid() = id` 就是“当前 JWT 的登录用户 ID 必须等于这行资料的 ID”。先有 `GRANT SELECT` 才能查询表；有了授权还需要 RLS policy 放行具体行。两道检查缺一不可。

`20260930131433_remove_teams_use_project_members.sql`、`20261003151530_project_roles_and_task_delete_permissions.sql` 和 `20261003151858_fix_project_owner_membership_policy.sql` 是业务权限迁移；`20261002103835_explain_current_project_permissions.sql` 只添加 SQL 注释。阅读时从头到尾按迁移顺序看，不要把某个老迁移单独当作线上最终状态；当前线上效果是全部迁移叠加后的结果。

## 授权规则

| 数据 | 未登录 | 登录但未加入项目 | 普通成员 | 项目 owner | 系统管理员 |
| --- | --- | --- | --- | --- | --- |
| 项目 | 无权访问 | 可读 ID/名称、可创建 | 可读、仍可自行加入 | 可读、创建、改名 | 可跨项目管理和永久删除 |
| 成员 | 无权访问 | 只能读自己的关系，可为自己加入 | 可读所在项目成员 | 可读本项目成员 | 可跨项目读取；角色管理待做 |
| 任务 | 无权访问 | 无权访问 | 可读写；只能删除本人任务 | 可读写并删除本项目全部任务 | 可跨项目管理 |
| 评论 | 无权访问 | 无权访问 | 可读/新增 | 可读/新增 | 通过全局任务访问判断可读/新增 |
| 用户资料 | 无权访问 | 只能读本人 | 可读共同项目用户 | 同普通成员 | 仍按共同项目关系读取 |

所有登录用户目前仍可浏览项目名称并自行加入。直接插入 `project_members` 时，RLS 强制 `user_id = auth.uid()`，普通加入默认为 `member`；`create_project(text)` 在同一事务创建项目并加入 `owner`。这是邀请功能完成前的过渡行为。下一个权限任务必须实现邀请加入并关闭公开发现和自行加入，再将项目列表收敛为本人创建/加入的项目。

如果 Auth 保持开放注册，任何新注册账号都可以看到项目名称并加入项目。任务删除角色限制已由 RLS 生效；开放发现/加入仍是明确的临时边界。

## 表授权和 RLS

- 未登录角色不获授业务表访问权限；`service_role` 不进入浏览器或 `VITE_*` 环境变量。
- `projects` 仅向 `authenticated` 授予读取 `id`/`name` 和按列创建/改名权限；RLS 允许 owner 改名、系统管理员跨项目管理/删除。
- `project_members` 允许读取自身、所在项目成员及系统管理员有权访问的成员；允许本人作为 member 加入，创建项目 RPC 只给创建者写入 owner；没有客户端删除/转让角色权限。
- `tasks`、`comments` 的 RLS 通过 `private.can_access_project` 和 `private.can_access_task` 确认成员或管理员访问；任务删除另检查创建者、项目 owner 或系统管理员。
- `profiles` 只允许本人插入和更新；资料读取仅限本人和共同项目成员。
- `create_project(text)` 是 `SECURITY INVOKER` RPC：插入项目并在同一事务中加入创建者，项目插入和成员插入都继续受 RLS 约束。

## 权限变更约定

1. 在 `supabase/migrations/` 创建迁移，并确认远程项目和本地迁移版本一致；不要改已经应用的迁移。
2. 检查列级 `GRANT`、RLS 的 `USING`/`WITH CHECK`、外键和删除级联。
3. 不把管理密钥放入浏览器；不以扩大到 `anon` 权限来修复访问错误。
4. 至少复核系统管理员、项目 owner、已有普通成员、新加入普通成员、未加入用户和未登录用户的访问范围。

## 邀请迁移应用后的权限（本地实现，尚未上线）

| 操作 | 普通未加入用户 | member | owner | 系统管理员 |
| --- | --- | --- | --- | --- |
| 项目读取 | 不可公开列出或按 ID 读取其他项目 | 自己加入的项目 | 自己所在项目 | 全部项目，允许未加入访问 |
| 我的项目列表 | 仅本人创建/加入 | 同左 | 当前 owner 显示 `(owner)` | 同样只列本人创建/加入，全项目入口后续实现 |
| 生成邀请 | 不允许 | 不允许 | 本项目可生成 | 任意现存项目可生成 |
| 接受有效邀请 | 以本人身份加入 member | 已加入则进入且不消费 | 已加入则进入且不消费 | 若尚无成员关系，兑换后作为 member 加入 |
| 直接写成员表 | 不允许 | 不允许 | 不允许 | 前端仍不获成员表写权限，成员管理独立任务实现 |
| 新建项目 | RPC 原子建立项目与 owner | 同左 | 同左 | 同左 |

邀请凭证位于 `private.project_invitations`，RLS 启用且不授予客户端表权限；只存 `SHA-256(hex(SHA-256(token)))`。浏览器发送第一层哈希进行兑换，数据库再哈希匹配并锁行；原始 token 不进兑换请求或日志，数据库保存的哈希也不能直接兑换。固定 24 小时、只一个新成员，已加入者不消耗。任务与评论规则沿用原有权限。

为关闭直接成员 INSERT，`create_project` 的 public RPC 保持 invoker，委托 private definer 完成经过身份校验的事务；不再依赖客户端表 INSERT GRANT/RLS。邀请写入也使用同样受限的包装形式。private schema 必须继续排除在 Data API 暴露列表外，不把 service_role 放进浏览器。
