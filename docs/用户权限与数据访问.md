# 用户权限与数据访问

> 核对日期：2026-10-01。当前权限模型只围绕项目成员；团队和团队成员表已从远程数据库删除。

## 部署状态

前端已部署至 Vercel：[tasks-board-swart.vercel.app](https://tasks-board-swart.vercel.app)。用户确认双账号可正常访问项目并进行操作；Supabase 注册验证回跳已按正式域名配置，建议抽查一封验证邮件确认最终跳转。

## 身份与数据模型

Supabase Auth 负责登录并提供 `auth.uid()`。表授权（`GRANT`）和 RLS 一起决定数据访问。

| 表 | 用途 |
| --- | --- |
| `profiles` | 用户显示名称，用户本人可修改。 |
| `projects` | 项目名称与创建者。所有登录用户可浏览项目 ID 和名称；创建者可改名、删除。 |
| `project_members` | 项目与用户的访问关系；成员只能为本人加入，不能替别人加入或移除成员。 |
| `tasks` | 项目任务；非空负责人必须是该项目成员。 |
| `comments` | 任务评论；访问范围继承任务所属项目。 |

团队模式迁移将原项目创建者、原团队管理员补为对应项目成员，保留项目权限；原项目成员、项目、任务和评论均保留。团队名称及仅有团队级别的成员记录已删除。

## 在哪里看表和权限

### Supabase Dashboard

在 Supabase Dashboard 选择 `kanban_board` 项目：

1. **Database → Tables**：查看 `public` schema 下的五张业务表和字段；选择具体表可查看结构及其 RLS policies。
2. **Database → Policies**（或表详情里的 Policies）：查看每条 RLS 规则的目标角色、操作类型和 `USING` / `WITH CHECK` 条件。当前已给表和策略写入数据库注释，帮助解释用途。
3. **Database → Roles**：查看 PostgreSQL 的 `anon`、`authenticated`、`service_role` 等数据库角色。这不是应用里的“系统管理员/项目组长/普通成员”角色列表。
4. **Authentication → Users**：查看 Supabase Auth 管理的登录用户。Auth 用户和 `public.profiles` 个人资料是相关但不同的记录。
5. **SQL Editor**：可以运行下面的只读查询复核策略和权限。

### SQL Editor 中的只读检查

查看当前 `public` 表的行级策略：

```sql
select tablename, policyname, roles, cmd, qual, with_check
from pg_policies
where schemaname = 'public'
order by tablename, policyname;
```

查看表级授权：

```sql
select grantee, table_name, privilege_type
from information_schema.role_table_grants
where table_schema = 'public'
  and grantee in ('anon', 'authenticated', 'service_role')
order by table_name, grantee, privilege_type;
```

有些授权只给特定列，因此还要单独查看列级授权：

```sql
select grantee, table_name, column_name, privilege_type
from information_schema.column_privileges
where table_schema = 'public'
  and grantee in ('anon', 'authenticated', 'service_role')
order by table_name, grantee, column_name, privilege_type;
```

查看系统角色是否绕过 RLS：

```sql
select rolname, rolsuper, rolbypassrls
from pg_roles
where rolname in ('anon', 'authenticated', 'service_role')
order by rolname;
```

这些查询只读。不要把数据库密码或 `service_role` key 贴进聊天、前端代码或 Git。

## PostgreSQL 角色与应用业务角色不是一回事

线上数据库已核对的角色和使用方式：

| PostgreSQL 角色 | 用途 | 当前项目里的权限 |
| --- | --- | --- |
| `anon` | 没有登录会话的 Data API 请求 | 当前五张业务表没有授予它应用读写权限。 |
| `authenticated` | 带有效 Supabase Auth 用户会话的请求 | 获得必要表/列授权，再由 RLS 限定到所有登录用户、项目创建者或项目成员各自能操作的行。它本身不区分项目组长和普通成员。 |
| `service_role` | 仅可信后端或 Supabase 内部管理操作使用 | 有广泛数据库权限并绕过 RLS；当前 Vercel 前端不使用它。绝不能把它放进 `VITE_*` 变量。 |

Supabase Dashboard 的项目拥有者/操作者也是平台管理权限，不是应用中登录的系统管理员。`service_role` 同样不是应用“系统管理员”角色，它是高权限技术密钥。

**当前数据库没有三种应用角色。** `project_members` 只有 `project_id`、`user_id`、`joined_at`，没有 `role` 字段；目前也没有全局系统管理员表。`projects.created_by` 只保存创建者 ID，并用于创建者项目级策略，不是完整的角色系统。

按线上数据库当前规则，`authenticated` 的应用权限可概括为：

| 表 | 登录且满足 RLS 的用户可以做什么 |
| --- | --- |
| `profiles` | 查看自己和共同项目成员的显示名；为自己创建资料、修改自己的显示名。 |
| `projects` | 浏览所有项目 ID/名称；创建项目；仅创建者可修改/删除自己的项目。删除项目会级联删除任务和评论。 |
| `project_members` | 查看自己的成员关系或所在项目成员；可以只为自己加入项目；没有通过客户端删除成员的权限。 |
| `tasks` | 项目成员可增删改查；可修改字段受列级授权限制。普通成员目前也能删除本项目任意任务。 |
| `comments` | 项目成员可查看和新增本人评论；当前没有普通登录角色的评论修改/删除授权及 RLS policy。 |

表/列授权和 RLS 是两层门：必须先有对应的 SQL 权限，再通过行策略。例如 `authenticated` 有权请求 `tasks`，但未加入项目时 RLS 不让它读取该项目任务。系统管理员如果需要跨项目管理，必须在应用层增加安全、明确的管理员判断和 RLS/服务端策略；不能因为把所有人改成 `authenticated` 就获得管理员能力。

## 已确认的目标业务权限（尚未实现）

这些是应用业务角色，不是 PostgreSQL 的 `anon`、`authenticated`、`service_role`。具体 SQL policy 和前端入口都要后续实现；当前规则仍以本页前面的“当前权限”为准。

| 目标角色 | 已确认的权限 |
| --- | --- |
| 系统管理员 | 管理全部项目与任务；账号管理暂缓。 |
| 项目组长 | 创建项目的人自动成为组长；可移除项目成员、转让组长、归档/恢复项目、永久删除项目。 |
| 普通成员 | 通过邀请加入项目后，可创建和修改任务、状态、负责人、评论；不能删除别人的任务。自己创建的任务可以删除。 |

项目列表改为“我的项目”：只显示本人创建或已加入的项目；本人创建的项目显示 `(owner)`。普通用户不再浏览或自行加入未关联的项目。项目创建与加入都要求登录，加入只通过邀请链接。

邀请链接采用随机、不可预测、一次性令牌，并设置有效期。不要把项目 ID 加密后当邀请码；加密/编码不等于可靠的一次性凭证。实现时令牌原文只出现在链接，数据库仅保存其哈希、项目、有效期、使用状态和创建者；兑换时在数据库事务中校验并同时加入成员、标记令牌已使用。

系统管理员的账号增删改和密码重置不属于当前范围；首位系统管理员如何安全指定需要在实现时通过 Supabase 受信任管理入口或受控 SQL 完成，不能在浏览器暴露 `service_role`。

### 读懂本项目的 Supabase 和 migration

可以先用 MySQL 的经验来对照：Supabase 底层仍是 PostgreSQL 数据库，但还帮项目提供登录认证、API 接口和 Dashboard。当前 React 页面通过 `supabase-js` 发请求；Supabase Auth 验证登录并给请求附上用户 JWT；PostgREST 把请求变成数据库查询；PostgreSQL 再检查 SQL 授权和 RLS，最后才读写表。

```text
React 页面 -> supabase-js + 当前登录 JWT -> Supabase Data API -> GRANT/列权限 -> RLS -> PostgreSQL 表
```

`supabase/migrations/` 下的 SQL 文件就是有版本号的数据库变更记录，类似“可追踪、可按顺序执行的数据库升级脚本”，不是第二个数据库，也不是 React 代码。Supabase CLI 按文件名前面的时间顺序把它们应用到远程数据库，并记录已执行版本。已经应用的迁移不要回头改；后续调整另建迁移，让本地文件和线上变更历史保持一致。数据库注释迁移只补充 Dashboard 里的说明文字，不改表数据和访问规则。

看迁移时建议按这个顺序读：

1. `create table` / `alter table`：创建表或改列、约束、外键。
2. `grant` / `revoke`：规定角色是否有资格对表/列发出查询或写入操作。
3. `alter table ... enable row level security`：启用逐行访问控制。
4. `create policy`：决定哪些行可读/写。`USING` 检查现有行；`WITH CHECK` 检查写入后行是否符合规则。
5. `create function`：把重复 SQL 封装为数据库函数；本项目的 `create_project(text)` 将建项目和添加创建者成员放进一次数据库调用中。

比如，仅允许用户读取自己的资料时，策略里的 `auth.uid() = id` 就是“当前 JWT 的登录用户 ID 必须等于这行资料的 ID”。先有 `GRANT SELECT` 才能查询表；有了授权还需要 RLS policy 放行具体行。两道检查缺一不可。

`20260930131433_remove_teams_use_project_members.sql` 是业务权限的主要迁移之一；`20261002103835_explain_current_project_permissions.sql` 只添加 SQL 注释。阅读时从头到尾按迁移顺序看，不要把某个老迁移单独当作线上最终状态；当前线上效果是全部迁移叠加后的结果。

## 授权规则

| 数据 | 未登录 | 登录但未加入项目 | 项目成员 | 项目创建者 |
| --- | --- | --- | --- | --- |
| 项目列表 | 无权访问 | 可读项目 ID 和名称 | 可读 | 可读、创建、改名、删除 |
| 项目成员 | 无权访问 | 只能读自己的成员关系，可为自己加入 | 可读取项目成员 | 同项目成员规则 |
| 任务与评论 | 无权访问 | 无权访问 | 可读写项目任务；评论可读和新增 | 同项目成员规则 |
| 用户资料 | 无权访问 | 只能读本人 | 可读同项目用户 | 同项目成员规则 |

所有登录用户可浏览项目名称并自行加入。项目加入在 `project_members` 上直接插入当前用户 ID，数据库 RLS 强制 `user_id = auth.uid()`；重复加入由主键冲突处理为幂等成功。加入后该用户才能读取项目任务、评论和同项目成员资料。双账号正常访问与操作已实测确认；未加入账号的拒绝边界仍建议单独验证。

如果 Auth 保持开放注册，任何新注册账号都可以看到项目名称并加入项目。项目数据仍受 RLS 保护，但这是开放加入模式的产品边界。

## 表授权和 RLS

- 未登录角色不获授业务表访问权限；`service_role` 不进入浏览器或 `VITE_*` 环境变量。
- `projects` 仅向 `authenticated` 授予读取 `id`/`name`，以及创建项目、修改/删除本人创建项目所需列权限。
- `project_members` 仅允许读取自身成员关系或已加入项目的成员关系；插入时必须是本人 ID，没有客户端删除权限。
- `tasks`、`comments` 的 RLS 通过 `private.can_access_project` 和 `private.can_access_task` 确认项目成员身份。
- `profiles` 只允许本人插入和更新；资料读取仅限本人和共同项目成员。
- `create_project(text)` 是 `SECURITY INVOKER` RPC：插入项目并在同一事务中加入创建者，项目插入和成员插入都继续受 RLS 约束。

## 权限变更约定

1. 在 `supabase/migrations/` 创建迁移，并确认远程项目和本地迁移版本一致。
2. 检查列级 `GRANT`、RLS 的 `USING`/`WITH CHECK`、外键和删除级联。
3. 不把管理密钥放入浏览器；不以扩大到 `anon` 权限来修复访问错误。
4. 至少复核项目创建者、已加入成员、未加入用户和未登录用户的访问范围。
