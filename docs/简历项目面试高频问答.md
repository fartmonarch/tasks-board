# React Kanban 简历项目面试高频问答

> 这份文档只整理面试官围绕本项目最可能继续追问的内容。每题先给代码定位和阅读注释，再给一段可以直接口述的简答。行号按 **2026-10-06** 当前源码记录；代码后续调整时请按函数名重新定位。

## 先准备一段项目介绍

**简答（约 40 秒）**：这是一个基于 React 和 TypeScript 的多人 Kanban 任务管理项目。用户登录后可以创建项目、邀请和管理成员，在看板里创建、编辑、筛选任务、评论，并通过拖拽调整任务状态和列内顺序。前端用 TanStack Query 管理服务端数据和缓存，用 Zustand 保存少量看板交互状态；数据和认证由 Supabase Auth、Postgres、Data API 与 RPC 提供，项目成员角色和 RLS 控制数据访问。拖拽后的顺序会写入数据库，因此刷新后仍能恢复。项目没有独立 Node 后端，也没有使用 Supabase Realtime；看板通过定时刷新读取协作者保存的数据。

**代码注释**：路由入口在 [`App.tsx`](../src/app/App.tsx#L42)，看板的数据查询和 mutation 集中在 [`BoardPage.tsx`](../src/features/tasks/pages/BoardPage.tsx#L48)，数据库请求封装在 [`taskApi.ts`](../src/features/tasks/api/taskApi.ts#L69)。介绍时说清楚“前端 + Supabase”即可，不要把它描述成有自建后端服务。

## 1. 这个项目的前端结构和一次任务查询是怎样的？

**代码定位与注释**

- [`App.tsx:42-60`](../src/app/App.tsx#L42)：注册项目列表、看板和邀请路由；路由入口调用各 feature 的页面。
- [`BoardPage.tsx:48-59`](../src/features/tasks/pages/BoardPage.tsx#L48)：页面拿到 `projectId` 后构造项目 Query，并根据登录用户和项目 ID 控制是否请求。
- [`BoardPage.tsx:82-100`](../src/features/tasks/pages/BoardPage.tsx#L82)：任务、成员等服务端数据分别用 Query 读取。
- [`taskApi.ts:69-79`](../src/features/tasks/api/taskApi.ts#L69)：`getTasks` 负责查任务表、按项目过滤、按排序字段排序，并映射为前端任务类型。

**简答**：路由层只负责把 URL 解析成页面参数；具体业务放在项目或任务 feature 页面中。以看板为例，`BoardPage` 用 TanStack Query 按用户和项目 ID 查询任务，真正的 Supabase 查询由 `taskApi.getTasks` 封装。这样页面处理交互和缓存，API 文件处理请求与数据映射，SQL migration 负责数据库结构和访问规则。

## 2. 为什么同时使用 TanStack Query 和 Zustand？分别放什么状态？

**代码定位与注释**

- [`BoardPage.tsx:52-59`](../src/features/tasks/pages/BoardPage.tsx#L52)：Query key 带有用户和项目 ID，避免不同用户或项目共用同一份看板缓存。
- [`BoardPage.tsx:87-100`](../src/features/tasks/pages/BoardPage.tsx#L87)：任务和成员来自服务端，因此用 Query 查询、刷新和缓存。
- [`BoardPage.tsx:101-115`](../src/features/tasks/pages/BoardPage.tsx#L101)：页面从 Zustand 读取搜索、筛选、当前打开任务等 UI 状态；表单和拖拽临时态留在本地 React state/ref。
- [`taskUiStore.ts:6-29`](../src/features/tasks/store/taskUiStore.ts#L6)：store 只定义搜索、状态筛选、选中的任务 ID 和对应操作。

**简答**：我按数据归属来分。服务器上的任务、项目和成员列表交给 TanStack Query，因为需要请求、缓存、刷新和 mutation 后更新；搜索条件、状态筛选、当前打开哪条详情属于界面状态，放在 Zustand。只在当前页面使用的输入框、编辑草稿和拖拽预览则放在组件本地，避免全局 store 变成所有状态的容器。

## 3. 登录状态怎么恢复？前端的权限判断够不够？

**代码定位与注释**

- [`AuthGate.tsx:13-23`](../src/features/auth/AuthGate.tsx#L13)：启动时调用 `getSession` 恢复会话，并监听 `onAuthStateChange`；卸载时清理订阅。
- [`AuthGate.tsx:25-35`](../src/features/auth/AuthGate.tsx#L25)：未配置、恢复中、未登录和已登录分别展示对应界面；已登录后通过 Context 提供 session。
- [`BoardPage.tsx:286-291`](../src/features/tasks/pages/BoardPage.tsx#L286)：页面根据归档状态、项目角色、任务创建者和管理员状态决定是否展示删除或拖拽操作。
- [`20261003151530_project_roles_and_task_delete_permissions.sql:159-169`](../supabase/migrations/20261003151530_project_roles_and_task_delete_permissions.sql#L159)：数据库删除策略按系统管理员、项目 owner、任务创建者等条件授权。

**简答**：应用启动时先恢复 Supabase session，再监听登录状态变化；已登录 session 通过 Context 提供给业务页面。页面上的权限判断主要用于控制按钮和交互体验，不能作为安全边界。真正的数据访问由数据库 GRANT 和 RLS policy 再校验，所以用户即使绕过前端直接请求，也不能仅凭隐藏或伪造按钮获得数据库权限。

## 4. 项目 owner、普通成员和系统管理员有什么区别？

**代码定位与注释**

- [`20261003151530_project_roles_and_task_delete_permissions.sql:4-6`](../supabase/migrations/20261003151530_project_roles_and_task_delete_permissions.sql#L4)：成员角色限定为 `owner` 或 `member`。
- [`20261003151530_project_roles_and_task_delete_permissions.sql:32-42`](../supabase/migrations/20261003151530_project_roles_and_task_delete_permissions.sql#L32)：每个项目最多一个 owner；系统管理员名单放在受保护的 `private.system_admins` 表。
- [`projectApi.ts:49-66`](../src/features/projects/api/projectApi.ts#L49)：前端分别查询当前用户是否为系统管理员及其项目角色，用于页面展示和交互判断。
- [`20261003151530_project_roles_and_task_delete_permissions.sql:159-169`](../supabase/migrations/20261003151530_project_roles_and_task_delete_permissions.sql#L159)：删除任务由数据库策略校验，不同身份能删除的范围不同。

**简答**：owner 是项目内的管理角色，member 是普通协作者；系统管理员是跨项目的应用级角色。前端查询这些身份是为了显示合适的入口，数据库策略负责最终授权。例如任务删除策略允许系统管理员、项目 owner 删除项目任务，普通成员只能删除自己创建且有权访问的任务。项目角色和系统管理员不是同一个概念。

## 5. 拖拽排序从手势到数据库保存，完整链路是什么？

**代码定位与注释**

- [`BoardPage.tsx:61-69`](../src/features/tasks/pages/BoardPage.tsx#L61)：配置鼠标、触屏和键盘 sensor，并为鼠标/触屏设置启动阈值。
- [`TaskCard.tsx:27-49`](../src/features/tasks/components/TaskCard.tsx#L27)：卡片通过 `useSortable` 绑定拖拽能力，实际拖动从单独的拖动手柄启动。
- [`BoardPage.tsx:297-350`](../src/features/tasks/pages/BoardPage.tsx#L297)：拖动经过目标卡片或状态列时，在本地预览同列重排或跨列移动。
- [`BoardPage.tsx:352-377`](../src/features/tasks/pages/BoardPage.tsx#L352)：拖动结束后检查顺序是否变化，更新 Query 缓存并触发保存 mutation。
- [`taskApi.ts:153-163`](../src/features/tasks/api/taskApi.ts#L153)：前端把项目 ID、任务 ID 列表和目标状态列表传给数据库 RPC。
- [`20261004084548_persist_task_sort_order.sql:24-32`](../supabase/migrations/20261004084548_persist_task_sort_order.sql#L24)：`reorder_project_tasks` 是 `SECURITY INVOKER` 函数，调用时沿用当前用户权限。

**简答**：拖动手势由 dnd-kit 传给看板；拖动过程中先更新本地预览，结束时检查任务顺序或状态是否真的变化。若有变化，就先更新 Query 缓存让界面立即响应，再调用 `reorder_project_tasks` 一次性保存项目内的任务 ID 和目标状态。RPC 在数据库事务中校验输入并批量更新状态和 `sort_order`，失败时前端恢复旧缓存并重新查询。

## 6. 为什么有搜索或筛选时禁用拖拽？排序字段怎么设计？

**代码定位与注释**

- [`BoardPage.tsx:255-261`](../src/features/tasks/pages/BoardPage.tsx#L255)：从完整任务列表按 `sortOrder` 排序，再生成筛选后的可见列表。
- [`BoardPage.tsx:291`](../src/features/tasks/pages/BoardPage.tsx#L291)：只在未归档、没有搜索词且状态筛选为全部时允许重排。
- [`20261004084548_persist_task_sort_order.sql:3-20`](../supabase/migrations/20261004084548_persist_task_sort_order.sql#L3)：新增 `sort_order`，按项目和状态分组回填旧任务顺序，并创建组合索引。
- [`20261004084548_persist_task_sort_order.sql:63-80`](../supabase/migrations/20261004084548_persist_task_sort_order.sql#L63)：RPC 检查传入任务数量与当前项目可见任务数量，并确认更新行数。

**简答**：搜索和状态筛选会隐藏部分任务；如果只拿当前可见子集重排并提交，可能覆盖整列的真实顺序。所以排序操作只对完整、未过滤的看板开放。数据库用 `sort_order` 保存任务在所属状态列中的位置，读取时按它排序；跨状态移动时 RPC 同时更新 `status` 和新位置。新增字段时还给已有任务按项目和状态回填了初始位置。

## 7. 多人同时操作时，界面如何看到对方的更新？这是实时推送吗？

**代码定位与注释**

- [`BoardPage.tsx:53-59`](../src/features/tasks/pages/BoardPage.tsx#L53)：项目查询设置定时刷新和窗口聚焦刷新。
- [`BoardPage.tsx:87-100`](../src/features/tasks/pages/BoardPage.tsx#L87)：任务及成员列表也设置定时刷新和窗口聚焦刷新。
- [`BoardPage.tsx:187-200`](../src/features/tasks/pages/BoardPage.tsx#L187)：排序写入失败时恢复 mutation 前缓存，并重新查询服务端数据。

**简答**：目前不是 Supabase Realtime 推送。看板通过 TanStack Query 定时轮询，并在窗口重新聚焦时刷新，因此协作者保存的更新会在下一次刷新后出现；手动刷新也可以主动拉取。拖拽保存失败时会回滚本地缓存并重新查询。这种方案实现简单，但更新可见会有轮询间隔带来的延迟；如果需要更低延迟，再考虑订阅推送。

## 8. 创建项目为什么通过数据库 RPC，而不是前端连续插入两张表？

**代码定位与注释**

- [`20261003151530_project_roles_and_task_delete_permissions.sql:131-157`](../supabase/migrations/20261003151530_project_roles_and_task_delete_permissions.sql#L131)：`create_project` 在一次函数调用内插入项目和对应的 owner 成员关系；函数以 `SECURITY INVOKER` 执行。
- [`projectApi.ts:89-100`](../src/features/projects/api/projectApi.ts#L89)：项目 API 调用创建流程并把数据库错误转换为业务错误。

**简答**：创建项目不仅要写 `projects`，还要马上给创建者建立 owner 成员关系。将这两步放在一个数据库函数中，可以让它们在同一个事务里一起成功或一起失败，避免留下“项目已创建但没人是 owner”的中间状态。函数使用 `SECURITY INVOKER`，因此仍受调用者数据库权限和 RLS 约束。

**简答**：我会从三层说明验证：前端 mutation 的成功、失败和缓存恢复；数据库 migration/RPC 的输入校验及 RLS 权限；再说明实际跑过的页面或数据库验收。这个仓库当前保留 lint 和 build 检查，但没有前端自动化测试套件，因此我不会把 lint/build 说成覆盖了完整交互，也不会把没有执行的浏览器验收说成已通过。具体有哪些账号场景和数据库操作验证过，要以阶段进度和权限验证记录为准。

## 面试时容易说过头的边界

- 这是 React 前端连接 Supabase 的项目，没有独立应用服务器；不要说成自己实现了 Node API 服务。
- 页面按钮的显隐只是用户体验；真正授权在数据库 GRANT/RLS/RPC。不要把“按钮被隐藏”说成权限安全。
- 协作者数据目前靠定时刷新同步，不要说项目已实现实时推送。
- 拖拽失败有缓存恢复和重新查询；不要把乐观界面更新描述成数据库已经成功写入。
- 只汇报自己实际验证过的项目场景、账号和命令。构建通过不等于浏览器、触屏、并发和跨账号验收全部通过。
