## 01：入口、路由和数据分工

### 图示问题与更正

- **文件名写错**：左上角 `AuthGate 恢复 session (App.tsx)` 应为 `AuthGate.tsx`。`App.tsx` 负责路由选择；会话恢复在 [`AuthGate.tsx:13-23`](D:/Code/project/react-kanban/src/features/auth/AuthGate.tsx:13)。

## 04：拖拽、保存与回滚

### 图示问题与更正

**这一张的问题主要在失败分支，不是拖拽手势本身。**

- **“事务成功”被错误地接到异常分支**：可见任务数量不一致时才抛 `40001`；更新数量不一致时才抛 `42501`；异常使整个事务回滚。所有检查通过才是成功，不能成功后再沿箭头进入失败回滚。分别见 [`排序 SQL:63-68`](D:/Code/project/react-kanban/supabase/migrations/20261004084548_persist_task_sort_order.sql:63)、[`79-82 行`](D:/Code/project/react-kanban/supabase/migrations/20261004084548_persist_task_sort_order.sql:79)。
- **B 区底部长红箭头不表示自动重新提交**：实际失败后是 `onError → setQueryData(previous) → exact invalidateQueries → 错误反馈`。源码没有回到 getQueryData 再自动 mutate 的循环；invalidate 是重新读取服务器数据。见 [`BoardPage.tsx:208-217`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:208)。
- **GRANT/RLS 是整个 UPDATE 的授权条件**：不是“事务成功或回滚之后”才执行的最后一步。图 C 右侧这块应读作旁注。
- **图中省略了两个细分分支**：数组不合法/状态不合法/重复 ID 抛 `22023`；提交任务数为 0 时直接返回。见 [`排序 SQL:40-58`](D:/Code/project/react-kanban/supabase/migrations/20261004084548_persist_task_sort_order.sql:40)。
- **cancelQueries 没有被 await**：源码用 `void queryClient.cancelQueries(...)` 发起取消，随后更新缓存和提交 mutation。图中的线性顺序不应理解成等待取消 Promise 完成后才继续，见 [`BoardPage.tsx:402-405`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:402)。

正确主线为：提交重排 → 参数校验 → 项目锁 → 数量校验 → 批量 UPDATE → 更新数量校验 → 成功返回。任一 SQL 异常或网络请求失败 → 前端恢复 previous 缓存并刷新查询。

### 正确实现与源码

- gate：[`BoardPage.tsx:299-307`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:299)、[`BoardPage.tsx:580-607`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:580) 要求未归档、无搜索、显示全部状态、无排序 pending。完整列表才能提交重排，避免隐藏任务导致位置覆盖。
- 预览算法：[`BoardPage.tsx:308-380`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:308) 识别目标任务或列，按卡片中心判断前后；同列修正索引再 arrayMove，跨列移出原列并改变 status 后插入。state 展示预览，ref 提供即时当前列表。
- 结束/取消：[`BoardPage.tsx:381-414`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:381) 对无目标、不可排序、pending 或无变化的情况清理预览；实际变化才抓旧快照、生成前端列内排序、调用 cancelQueries、setQueryData，再提交 mutation。
- 回滚：[`BoardPage.tsx:200-217`](D:/Code/project/react-kanban/src/features/tasks/pages/BoardPage.tsx:200) 的 onMutate 保存 previous context；失败恢复旧缓存并 exact invalidate，使服务器数据最终校准。
- RPC wrapper：[`taskApi.ts:153-163`](D:/Code/project/react-kanban/src/features/tasks/api/taskApi.ts:153) 只传项目 ID、任务 ID 数组与对应状态数组，不直接传前端 sortOrder。
- 数据库排序：[`20261004084548_persist_task_sort_order.sql:24-88`](D:/Code/project/react-kanban/supabase/migrations/20261004084548_persist_task_sort_order.sql:24) 是 SECURITY INVOKER；校验等长、状态、NULL、重复 ID，取得项目级事务 advisory lock，检查当前可见任务数量，再批量 UPDATE；更新行数不匹配抛错，整次事务回滚。授权继续依赖 tasks UPDATE GRANT/RLS。
- **排序值细节**：前端即时缓存按每个状态列从 0 计数；RPC 用整个提交数组的 `WITH ORDINALITY` 写 `position-1`。数据库值不保证每列都从 0 连续，但列内相对顺序不变。
- **并发边界**：advisory lock 防止两次重排交错更新；数量匹配不检查版本，所以同数量的并发重排仍可发生后写覆盖。普通创建/状态修改的 max+1 没用同一项目锁，也没有 sort_order 唯一约束；图不把这套实现描述成无冲突多人排序。
